Module 03 · Caching

Caching. Fast reads, honest trade-offs.

A database read crosses the network and may touch disk. A cache keeps hot results in memory, so repeated reads skip the database entirely. The cost is that the copy can go out of date.

Memory is orders of magnitude faster than a database round trip. Most read traffic hits a small set of keys, so caching that set takes most of the load off the database.

Read product:1. The cache is cold, so the first read goes to the database.

Stale reads

Write a new price for product:1, then read it again. The cache still returns the old value, because nothing told it the database changed.

Two standard controls: give every entry a TTL so stale data has a maximum age, and invalidate (delete) the key on every write so the next read refetches it.

In a design review "The workload is read-heavy, so I'll put Redis in front of the database using cache-aside: read from cache, fall back to the database on a miss, then populate the cache. Entries get a TTL, and writes invalidate the key to bound staleness."
